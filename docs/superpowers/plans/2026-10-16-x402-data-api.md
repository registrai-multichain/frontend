# x402 Paid Extras Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sell deep history, a bulk day export and watch-feed data per call through x402 on builder.registrai.cc (HTTP
and MCP). Buyers pay with Circle Gateway Nanopayments or standard EIP-3009 USDC, and we settle the standard path
ourselves.

**Architecture:**
- **One payment gate** (`x402-gate.ts`) wraps each paid product in the Pages Functions:
  - with no payment, it builds the 402 (two `accepts`);
  - with a payment, it verifies, records the payment once in D1, settles, and only then serves.
- **Circle path:** `BatchFacilitatorClient`.
- **Standard path (ours):** viem verifies the EIP-712 signature, and our gas wallet submits
  `transferWithAuthorization`.
- **Products** reuse the v1 handlers (with the window cap lifted), plus a proxy to the watch-feed API on the server.

**Tech Stack:**
- Cloudflare Pages Functions (TS), D1 (`registrai-data`), KV;
- `@circle-fin/x402-batching@^3.5.0`, `@x402/core@^2.28.0` (http header codecs);
- `viem` (already a dependency);
- vitest.

**Spec:** `docs/superpowers/specs/2026-10-16-x402-data-api-design.md` (approved 2026-10-16, "Good").

## Global Constraints

- **The free tier is unchanged.** No current route, tool, window or limit changes behaviour.
- **Network:**
  - mainnet: `eip155:5042`, with Circle facilitator `https://gateway-api.circle.com`;
  - testnet: `eip155:5042002`, with `https://gateway-api-testnet.circle.com`;
  - chosen by `X402_NETWORK` (`arc` | `arcTestnet`, default `arc`).
- **Assets:**
  - USDC is `0x3600000000000000000000000000000000000000` on both networks, with 6 decimals in amounts (e.g.
    $0.01 = `"10000"`);
  - the EIP-712 domain `name`/`version` are read from the chain (`name()`/`version()`), never hard-coded.
- **Prices in microUSDC** (Circle / standard):

  | Product | Circle | Standard |
  |---|---|---|
  | deep_index_history | 2000 | 10000 |
  | deep_member_history | 2000 | 10000 |
  | members_day | 30000 | 50000 |
  | events | 2000 | 10000 |
  | contract | 5000 | 10000 |
  | project_scope | 10000 | 20000 |

- **Unconfigured:** when `X402_PAY_TO` is unset or not an address, every paid route answers **503**
  `{ error: "Payments are not configured yet." }`, and no 402 is issued.
- **Standard settlement** also needs `X402_SETTLER_KEY` (a secret). If it is unset, the 402 offers only the Circle
  entry.
- **Ledger:**
  - D1 table `x402_payments`, unique `(scheme, payer, nonce)`;
  - a duplicate gives 402 `payment already used`;
  - data is served only after `status = settled`.
- **Headers:**
  - v2 `PAYMENT-REQUIRED` (base64 JSON) on 402, with the same JSON in the body;
  - the request carries `PAYMENT-SIGNATURE`, or v1 `X-PAYMENT`;
  - the success response carries `PAYMENT-RESPONSE`.
  - Use the `@x402/core/http` codecs.
- **Secrets are never logged.** Logs show payer and tx hash only. Workers have no `process`, and
  `test/worker-imports.test.ts` must stay green.
- **Tests and deploy:** the full suite may fail only on `src/lib/drafts.test.ts`, and lint must be clean. Deploy
  from `.worktrees/abi-deploy`, following the standard steps.

## Review Focus

1. **Signature replay:** the same signed authorization sent twice, or concurrently, is charged once. The second
   request gets 402 `payment already used`, never data for free. Pinned in Task 3.
2. **Underpay or wrong payee:** `value` below the price, `to` ≠ `payTo`, the wrong network or asset, or an expired
   `validBefore` gives 402 with a reason, and nothing is submitted. Pinned in Task 3.
3. **Settlement unknown** (send OK, receipt timeout): no data is served, and the status is `unknown`. A later retry
   with the same nonce reconciles through `authorizationState` and serves if it was used for our `payTo` and amount.
   Pinned in Task 3.
4. **The gas wallet is empty or the RPC is down:** 402 `settlement_failed`, no data, nothing charged, and the health
   endpoint reports it. Pinned in Task 4.
5. **The watch-feed backend is down:** settlement must not happen before the product is known to be available.
   Paid proxy routes check upstream health before settling and answer 503 without charging. Pinned in Task 5.

### Task 3: Standard path: verify, settle, reconcile (EIP-3009)

**Files:**
- Create: `builders-site/lib/x402-eip3009.ts`
- Test: `builders-site/test/x402-eip3009.test.ts`

**Interfaces:**
- Consumes: `Requirement`; the Task 1 ledger.
- Produces:
  - `type Eip3009Payload = { signature: `0x${string}`; authorization: { from; to; value: string; validAfter: string; validBefore: string; nonce: `0x${string}` } }`;
  - `interface ChainIO { authorizationState(from, nonce): Promise<boolean>; submit(payload: Eip3009Payload): Promise<`0x${string}`>; receipt(tx): Promise<"success"|"reverted"|"pending"> }`;
  - `verifyEip3009(p, req: Requirement, chainId: number, now: number, io: ChainIO)`, which returns
    `Promise<{ ok: true; payer } | { ok: false; reason }>`. It checks:
    - the EIP-712 signature (`verifyTypedData`, domain `{ name, version, chainId, verifyingContract: asset }`,
      type `TransferWithAuthorization`);
    - `to == payTo` (case-insensitive) and `BigInt(value) >= BigInt(req.amount)`;
    - `validAfter <= now < validBefore`;
    - `!await io.authorizationState(from, nonce)`.
  - `settleEip3009(db, p, req, product, io, opts)`, which returns
    `Promise<{ ok: true; tx } | { ok: false; reason: "payment already used"|"settlement_failed"|"settlement_unknown" }>`.
    It goes: `reserve`, then `submit`, then poll `receipt` (up to `opts.waitMs`, default 8000), then
    `markSettled`/`markFailed`.
    - A duplicate reserve whose existing row is `unknown` triggers reconciliation: if
      `authorizationState(from, nonce)` is true (the transfer happened), mark it settled and return ok, with the tx
      unknown.
  - `viemChainIO(env, cfg)`, the real implementation over viem `createWalletClient` (account from
    `cfg.settlerKey`, `fallback` transport Blockdaemon then public RPC) and `writeContract(transferWithAuthorization)`.

- [ ] **Step 1: Failing tests.** Use a fixed test key, `privateKeyToAccount("0x" + "11".repeat(32))`, to sign real
  EIP-712 authorizations in the test.
  1. A valid signature passes, and settle returns ok with the tx; the ledger row is `settled`.
  2. Wrong `to`, underpay, expired, not yet valid, a bad signature, or a used onchain nonce each fail with their
     reason, and `submit` is not called.
  3. A replay of the same payload gives `payment already used`, and `submit` is called once in total, also when two
     settles run concurrently.
  4. A reverted receipt gives `settlement_failed` with the row `failed`. A pending receipt past `waitMs` gives
     `settlement_unknown` with the row `unknown`.
  5. A retry after `unknown` with `authorizationState` now true gives ok, with the row `settled`.
- [ ] **Step 2:** Run the tests; they FAIL.
- [ ] **Step 3:** Implement, using the EIP-3009 typed-data definition:
  ```ts

    { name: "validAfter", type: "uint256" }, { name: "validBefore", type: "uint256" }, { name: "nonce", type: "bytes32" } ] } as const;
  ```
- [ ] **Step 4:** Run the tests; they PASS.

### Task 4: Circle path and the payment gate

**Files:**
- Create: `builders-site/lib/x402-gateway.ts`, `builders-site/lib/x402-gate.ts`
- Test: `builders-site/test/x402-gate.test.ts`

**Interfaces:**
- Consumes: Tasks 1–3.
- Produces:
  - `settleGateway(db, payload, req, product, client: Pick<BatchFacilitatorClient, "verify"|"settle">)`, which
    returns `Promise<{ ok: true; tx } | { ok: false; reason }>`. It goes: verify, then reserve (the nonce comes from
    `payload.payload.authorization.nonce`, else a sha256 of the payload), then settle, then mark.
  - `payGate(req, env, deps, product, serve: () => Promise<Response>, opts?: { precheck?: () => Promise<Response | null>; io?: ChainIO; gateway?: … })`,
    which returns `Promise<Response>`:
    1. If the config is null, return 503 `"Payments are not configured yet."`.
    2. Read the payment header (`PAYMENT-SIGNATURE` or `X-PAYMENT`) and decode it with `decodePaymentSignatureHeader`.
    3. With no header, return `respond402(paymentRequired(...), "Payment required")`.
    4. Pick the path by `payload.accepted?.extra?.name === "GatewayWalletBatched"`, or by the payload shape (an
       `authorization` plus `signature` means eip3009).
    5. Run `opts.precheck()` before settling. If it returns a Response (e.g. upstream down → 503), return it
       without charging.
    6. Settle. On `ok`, call `serve()`, then attach `PAYMENT-RESPONSE`
       (`encodePaymentResponseHeader({ success: true, transaction, network, payer })`), and copy the response.
    7. On failure, return `respond402` with the reason.
  - `paidHealth(env, io)`: `{ configured, network, settler_balance_usdc, low: balance < 2 }`, with no secrets.
